Main and backup: redundancy for Pro Tools playback

There is a sentence that gets repeated in this trade because it is true: if my laptop dies, there is no show. That is the whole argument for redundancy, and it is why productions with real budgets treat a backup machine as a line item rather than a nicety.

The trouble is that "we have a backup" is four different claims wearing one coat, and most rigs have some of them and not others. This is how to tell which ones you actually have.

Redundancy is four layers, not one

Separate them before you buy anything.

Layer 1 — Audio. If the main machine stops producing sound, does sound keep coming out of the same console inputs? This is the layer that determines whether the audience hears a failure.

Layer 2 — The machine. Is there a second computer, already running, already loaded, already in the right place in the session? Not "in the case." Running.

Layer 3 — Sync. When you switch, is the backup at the same position in the same song? A backup two bars behind is not a backup.

Layer 4 — Operator state. Tonight's running order, the songs you cut at soundcheck, which songs stop at the end and which run on, the screen dimmer setting. This is the layer nobody plans, because it lives in one person's screen and one person's head.

Most rigs solve 1 and 2, half-solve 3, and completely ignore 4. Layer 4 is the one that makes a failover look wrong to the band even when the audio was flawless: the music kept playing, but the screen on stage is now showing last night's set order.

Layer 1: switching the audio

This is a hardware problem and it should stay a hardware problem. The standard answer in touring playback is a dedicated redundancy audio interface — a box that takes outputs from both machines, feeds one set of outputs to the console, and switches from main to backup when the main stops sending a heartbeat. Expert Sleepers' PlayAUDIO12 is the widely used example of the category.

Two things about it are worth stating plainly:

  • It switches audio, and only audio. It knows nothing about your session, your setlist or your screens.
  • The switch is only as good as the heartbeat. A machine that has locked up while still outputting audio will not trigger a switch. Rehearse the ugly failure (frozen but alive), not just the clean one (power cut).

If a hardware switcher is out of budget, the manual version is a console with both machines patched to separate input banks and a rehearsed "swap to backup inputs" move. That is a real plan. Time it and write the number down.

Layer 2: the second machine

The backup is a machine with the same Pro Tools version, the same session, the same I/O setup, the same plug-ins, the same OS-level hygiene, running, from the top of the show. Not asleep. Not on the last song's project.

Things that quietly break this:

  • Session opened on the backup before the last round of marker edits. Now the two machines disagree about where song 9 is.
  • Different Pro Tools versions. Sessions open, but something behaves differently under pressure.
  • A plug-in authorised on one machine and not the other, and the difference is discovered at the moment you switch.
  • The backup's display asleep because nobody has touched it in two hours.

The cure is a written build sheet for the show machine and a rule that any change made to one is made to both, the same day, before you leave.

Layer 3: staying in the same place

Two independent machines drifting apart is the failure that makes redundancy useless.

The clean approach: both machines chase the same timecode. One master source, both Pro Tools rigs locked to it, so the backup's playhead is where the main's playhead is at all times. If they are locked, a switch is a switch and nothing else happens.

The pragmatic approach many shows actually use: both machines run their own transport, started together, on stable clocks, and the operator accepts a small drift and switches at a song boundary rather than mid-song. This is fine and honest as long as everyone knows that mid-song failover means a musical bump.

The dangerous middle: a backup that looks synced because it is following something derived from the main machine. If the backup's position ultimately comes from the main, then when the main dies, the backup freezes with it — and it will look perfect in every test you ran while the main was alive. This is a genuine, easy-to-make wiring mistake. The diagnostic is simple: stop the main machine only, and confirm the backup's position keeps moving on its own. If it stalls a second or two later, your backup was never independent.

Layer 4: the operator state everyone forgets

You cut two songs at soundcheck. You moved the encore. Song 6 is set to run straight into song 7 tonight because the band asked. The screen dimmer is at 40% because the LD asked.

None of that is in the Pro Tools session. It is in the operator's app, or on a piece of paper, or in the operator's memory. When the main machine dies at song 11, the person who takes over has the audio, has the timeline, and has none of tonight's decisions.

The manual mitigation, and it is a decent one: a printed running order in the backup position, updated after soundcheck, initialled. Cheap, offline, and unavailable to nobody. Do it regardless of what software you run.

The drill

Redundancy that has not been drilled is a belief, not a system. Run this once per tour, and again after any rig change. Twenty minutes with the band, or at the end of soundcheck.

  1. Clean kill. Mid-song, cut power to the main machine. Did the audio continue? How many seconds of anything? Who noticed on stage?
  2. Dirty kill. Mid-song, freeze the main machine without killing its outputs (hold it in a modal state, pull its network, whatever your rig allows). Did the switcher do anything? This is the failure that catches rigs out.
  3. Position check. After the switch, is the backup in the same bar? Write down the offset.
  4. State check. Does the backup have tonight's running order, or last rehearsal's?
  5. Recovery. Bring the main back. Does anything switch back unexpectedly? An automatic switch-back mid-song is worse than the original failure.
  6. Who decides. State out loud who is allowed to declare a failover and who does the promoting. One person.

Note point 6 carefully. There is a reason serious systems favour manual promotion: automatic failover means a machine gets to make a show-stopping decision on incomplete information, and the classic result is both machines deciding they are in charge. A human who can see the room takes about two seconds and is right far more often.

Where our tool sits — and where it does not

Prossible works on layer 4, and on nothing else. It is worth being blunt about that, because redundancy is exactly the wrong place for marketing vagueness.

What it does: pair a main and a backup Mac over the local network. Each Mac runs its own Pro Tools and follows its own MTC — the backup is never watching the main's screen, which is precisely the dangerous middle described above, and we designed against it deliberately. What syncs between them is the operator state: running order, per-song colours, skips, end-of-song behaviour (stop or run on), mode and dimmer. Changes on the active console appear on the standby within about a second.

When the main disappears, the backup's badge changes to STANDBY — LINK LOST within five seconds. Its music and stage display do not stop, because they were never dependent on the main. You then press Promote to Active — a person, deliberately, never automatically. If the old main comes back, it reconnects and settles quietly into standby without a single popup, inheriting whatever changed while it was gone. If both consoles were promoted while separated, both show a red SPLIT BRAIN badge rather than silently picking a winner; you resolve it by promoting the one that should lead.

What it does not do, and will not claim to: switch your audio, mirror your Pro Tools transport, or replace layers 1 through 3. Your audio and MIDI redundancy stay exactly where they are.

Requirements: macOS 15 or later on Apple silicon, Pro Tools 2023.6 or later with PTSL, on each machine.
